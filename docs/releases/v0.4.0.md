# Monitor Hub 0.4.0

Monitor Hub 0.4.0 is the next stable release after 0.3.0. The main change is a new project-scoped Agent Channel architecture: each monitored project can stay attached to the Agent/session that originally created the monitoring request, instead of creating a separate one-shot headless model process for each later project question.

## Project-scoped Agent Channels

Each project now gets an isolated durable conversation channel under Monitor Hub data:

```text
MONITOR_HUB_DATA/agent-channels/<safe-project-id>/
  binding.json
  messages.jsonl
```

`binding.json` identifies the originating Agent/session. `messages.jsonl` stores append-only project conversation/context.

This makes project conversations durable across UI refreshes and process restarts while keeping project identities isolated.

## Originating-Agent binding

When a new monitoring request is created from a recognized active Agent workspace, Monitor Hub records origin metadata and binds the resulting stable project ID to that Agent/session.

This allows one originating Agent to own multiple monitoring requests while still giving every project its own logical identity:

```text
project-agent:<project_id>
```

Project context is not shared across projects.

## Qt project conversation changes

The former one-question/one-headless-model project Q&A path is replaced by a **Project Agent** conversation surface.

For the selected project, the desktop UI can render:

- the original monitoring request;
- normalized Monitor Hub state;
- optional read-only live-query context;
- user questions/instructions;
- Agent replies written back to the bound project channel.

The Qt UI itself no longer launches a fresh model CLI process for every project question.

## Stable callable interface

0.4.0 adds a local file-backed Agent integration surface intended for MCP/Agent hosts:

- `--agent-channel PROJECT`
- `--agent-pending PROJECT`
- `--agent-post PROJECT --message/--message-file`
- `--agent-reply PROJECT --reply-to MESSAGE_ID --message/--message-file`
- `--agent-bind PROJECT --binding-file FILE`
- `--agent-kind`
- `--agent-source`
- `--agent-correlation`

The channel is local IPC through durable files. It does not introduce a network listener.

## Authority and safety

The new Agent Channel carries conversation and context only. It does **not** grant new execution authority.

Existing control boundaries remain unchanged:

- L1 deterministic/pre-authorized actions;
- L2 policy-bounded Agent actions;
- L3 main-Agent/user decisions;
- `agent action finished != issue resolved`;
- recovery still requires downstream verification.

Operational mutations continue to use the existing command/control path.

## Compatibility

0.4.0 is additive relative to 0.3.0:

- project registry schema remains compatible;
- Agent/Event Protocol v1 remains unchanged;
- command IDs and event semantics remain unchanged;
- updater manifest and Windows package layout remain unchanged;
- existing projects without Agent bindings continue to work;
- projects can be bound later;
- Windows-unsafe project-ID characters are encoded safely in channel directory names;
- project/workspace/runtime data remain outside the managed release payload.

## Upgrade from 0.3.0

0.3.0 users can upgrade directly to 0.4.0 through the stable updater or the new Windows installer.

Existing project data, workspaces, logs, local Hub runtime data, and scientific/business outputs are not part of the managed application payload and are preserved during normal upgrade/uninstall behavior.

Development checkouts containing `.git` remain protected from self-overwrite.
