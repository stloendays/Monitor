# Monitor Hub 0.2.1

Monitor Hub 0.2.1 is a patch release on top of 0.2.0. It keeps the same Windows packaging and update contracts while adding the final user-facing automatic recovery status layer that landed immediately after 0.2.0 was published.

## Recommended download

| User | File | Notes |
|---|---|---|
| Windows user | `Monitor-Hub-0.2.1-win64-setup.exe` | Recommended installer. Per-user install, no administrator rights required. |
| Portable use | `Monitor-Hub-0.2.1-win64-portable.zip` | Extract and run `MonitorHub\bin\monitor_hub_qt.exe`. |
| Monitor Hub updater | `monitor-hub-windows-x64.zip` | Stable updater payload; not intended as a normal manual install archive. |
| Integrity verification | `SHA256SUMS.txt` | SHA-256 checksums for the release assets. |

## What changed in 0.2.1

### Automatic recovery lifecycle UI

The **问题与 Agent / Issues & Agents** area now includes a dedicated automatic recovery projection above the detailed issue/event timeline.

It shows, per issue:

- task and issue identity;
- recovery chain;
- current recovery stage;
- expected next step;
- current authority level.

The UI now distinguishes stages such as:

`detected -> classified -> assigned -> agent_handling -> action_selected -> waiting_verification -> recovery_verified -> resolved`

and keeps decision-gated or failed paths visible.

### Independent recovery verification remains explicit

The patch makes an important control-plane invariant visible in the UI:

`agent.completed`, `issue.action_applied`, and `task.restarted` do **not** imply that an issue is recovered.

After an automatic action, the UI can explicitly show **action completed, waiting for recovery verification** until downstream evidence confirms `issue.recovery_verified` and ultimately `issue.resolved`.

### Better attention correctness

If later protocol facts prove that a decision has already been acted on, stale “waiting for user” state is cleared. This prevents the desktop UI from presenting an obsolete L3 decision request while recovery is already underway.

### Compatibility

0.2.1 is additive relative to 0.2.0:

- no Protocol v1 JSON field changes;
- no command/event ID changes;
- no recovery-policy authority expansion;
- unknown events remain preserved;
- updater asset name and manifest format are unchanged;
- install layout is unchanged.

The stable release pipeline validates:

- SemVer identity from root `VERSION`;
- C++/Qt Release build;
- full CTest suite including recovery projection tests;
- compiled CLI version;
- Windows installer and portable packaging;
- updater manifest and per-file SHA-256;
- staged desktop diagnostics;
- silent install -> installed diagnostics -> uninstall;
- release checksums;
- stable publication only from canonical `main`.

## Upgrade from 0.2.0

0.2.0 users can upgrade directly to 0.2.1. Project/workspace data is not part of the managed application payload and is not removed during upgrade or uninstall.

For development checkouts containing `.git`, continue using Git to update source code; the release updater must not overwrite a development checkout.
